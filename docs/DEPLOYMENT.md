# Implantação

O `compose.yaml` é somente para desenvolvimento local em HTTP (`localhost:8088`). Ele agora executa `migrate` uma vez antes de iniciar `api-1` e `api-2`, com balanceamento pelo Caddy. O serviço `migrate` usa a mesma imagem da API com `--migrate`; instâncias HTTP nunca aplicam migrations ao iniciar. As chaves de Data Protection são compartilhadas por volume entre as duas instâncias no mesmo host.

`compose.production.yaml` é uma **base de implantação em uma VPS**, com Caddy HTTPS, duas APIs, migrations isoladas, limites iniciais de recursos e logs JSON do proxy. Exige `SITE_DOMAIN`, `ACME_EMAIL`, `POSTGRES_PASSWORD`, `POSTGRES_REPLICATION_PASSWORD`, `REDIS_PASSWORD` e `RABBITMQ_PASSWORD` definidos fora do repositório. Execute `docker compose -f compose.production.yaml config --quiet` e revise migrations/backup. Depois rode `docker compose -f compose.production.yaml build`, `docker compose -f compose.production.yaml run --rm migrate` e, somente se a migração terminar com sucesso, `docker compose -f compose.production.yaml up -d --no-build`. O perfil `migration` impede que um `up` comum repita migrations. Verifique `/health/ready` pelo domínio HTTPS e falha de uma instância sob tráfego.

Essa configuração não é HA: proxy, PostgreSQL primary e host são pontos únicos de falha. O volume de chaves só atende réplicas no mesmo host. Para múltiplas VPS, substitua banco e chaves por serviços/armazenamento compartilhados com proteção adequada, configure proxy redundante e teste failover. Cada API limita seu pool Npgsql a 20 conexões no primary (40 entre duas APIs); ajuste esse teto com medições, reservando conexões para migração e administração antes de adicionar instâncias. A réplica PostgreSQL, o Redis e o RabbitMQ locais estão descritos em `docs/architecture/distributed-services.md`; PgBouncer continua pendente de medição.

O worker de pagamentos tem pool máximo de 5 conexões e inicia sem processador quando `PAYMENT_WEBHOOK_ENABLED=false` (padrão). Para habilitar a recepção de webhook, configure `MERCADO_PAGO_ACCESS_TOKEN`, `MERCADO_PAGO_WEBHOOK_SECRET` e `PUBLIC_SITE_URL` HTTPS, além de `PAYMENT_WEBHOOK_ENABLED=true`, e teste assinatura, inbox, retries, duplicatas e reconciliação em sandbox. Habilitar o webhook **não** habilita checkout. Monitore notificações com `Outcome=Mismatch` ou `ConflictingPayment` e tentativas acumuladas; exigem revisão humana. Não execute cancelamento automático de reserva sem verificar o estado do pagamento no provedor.

Antes de publicar: concluir checkout e administração; executar migrations em etapa controlada; Caddy HTTPS com domínio real; segredos e credenciais de provedores; backups automáticos com cópia externa e restauração testada; health checks dos containers; limites de recursos; política de atualização e rollback; páginas legais revisadas.

As configurações Compose e os dois Caddyfiles passaram em validação sintática. Um stack isolado com duas APIs foi iniciado, testado com uma instância parada e removido; os containers de desenvolvimento preexistentes foram preservados. O resultado está em `docs/architecture/load-testing.md`. Não foi executado deploy de produção nem teste de carga representativo.
